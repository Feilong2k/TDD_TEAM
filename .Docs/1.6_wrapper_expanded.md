## 2. JSON Files Created and Their Structure

The system uses several JSON files to keep track of projects, tasks, and conversations.

### tasks.json

**Fields:**

**Each Task Contains:**
- `id`: Unique identifier for the task

- `created_at`: When the task was created (timestamp)
- `updated_at`: When the task was last updated (timestamp)

## 3. Response JSON We Expect from Orion

Orion must always respond with JSON in a specific format. This ensures your system can automatically process his responses.

### The Response Structure:
Every response from Orion has three main parts:

1. **response_type**: Tells us what kind of response this is
   - `clarification`: Orion needs more information (asks questions)
   - `decomposition`: Orion breaks a task into smaller subtasks
   - `instruction`: Orion gives detailed steps for Tara or Devon to follow
   - `status_update`: Orion updates the status of a task or subtask
   - `conversation`: General chat response or explanation

2. **content**: The actual information, which varies by response type
   - For `clarification`: An array of questions Orion wants answered
   - For `decomposition`: An array of subtasks (each with id, title, description, assignee, and status)
   - For `instruction`: Step-by-step instructions for Tara or Devon
   - For `status_update`: An array of status changes (task/subtask id and new status)
   - For `conversation`: A plain text message for the user

3. **metadata**: Additional information about the response
   - `task_id`: Which task this response relates to (or null if not task-specific)
   - `project_id`: Which project this is for
   - `requires_action`: Whether the user needs to do something next (true/false)
   - `next_step`: A brief description of what should happen next

### Example Response Types:
- **Clarification**: "I need to know: Should we support social login?"
- **Decomposition**: "Break 'user authentication' into: 1) Write failing tests, 2) Implement login, 3) Test integration"
- **Instruction**: "Tara, write Jest tests for the login endpoint that expect 400 on invalid credentials"
- **Status Update**: "Task T-001 is now in_progress"
- **Conversation**: "I understand you want to add user authentication. Let me help you break that down."

## 4. The Prompt We Built for Orion

The prompt tells Orion who he is, what his job is, and how he should respond.

### Orion's Role:
- He is an expert in Test-Driven Development (TDD) and software engineering
- He works with two teammates: Tara (writes tests) and Devon (implements code)
- He is the "brain" of the operation - he analyzes tasks, asks questions, breaks them down, and coordinates between Tara and Devon

### Key Instructions to Orion:
1. **Always respond in JSON format** - never use markdown, code blocks, or plain text outside the JSON structure
2. **Ask clarification questions first** if requirements are unclear
3. **Break tasks into at most 3 subtasks** following the TDD pattern: test → implement → test
4. **Assign subtasks** to either Tara (for tests) or Devon (for implementation)
5. **Update task status** when appropriate
6. **Keep responses focused and actionable**

### The Prompt Construction:
1. Starts with Orion's system prompt (his role and instructions)
2. Adds any previous conversation history (if available)
3. Includes the new user message
4. Ends with: "Orion (respond in JSON only):"

This structure ensures Orion has all the context he needs while maintaining the required response format.

## Additional Important Information

### Error Handling:
- If Orion doesn't respond with valid JSON after two attempts, the wrapper returns a friendly error message to the user
- All errors are logged to `data/logs/orion_errors.log` for troubleshooting
- The system continues working even if one message fails

### File Monitoring Script:
- A separate script (`sample-polling.js`) watches the `tasks.json` file for changes
- When the file changes (indicating new tasks or status updates), it can automatically trigger Cline to continue working
- This enables automated workflows where file changes trigger the next steps

### Integration Points:
1. **Chat Interface** → Backend API: User types message, frontend sends to backend (`/api/chat`)
2. **Backend API** → Orion Wrapper: Backend calls the wrapper with message, project, task, and mode
3. **Orion Wrapper** → HTTP Proxy: Wrapper sends Cline command array to proxy server on VM
4. **HTTP Proxy** → Cline: Proxy executes Cline command on VM (non-interactive, with JSON output format)
5. **Cline** → Orion: Cline communicates with AI models
6. **Orion** → Cline: Returns JSON response
7. **Cline** → HTTP Proxy: Returns stdout/stderr
8. **HTTP Proxy** → Orion Wrapper: Returns JSON with exit code and output
9. **Orion Wrapper** → Backend API: Returns parsed JSON response
10. **Backend API** → Chat Interface: Returns formatted response to user

### Proxy Server:
A secure HTTP proxy runs on the VM at `192.168.0.4:9001` and provides two endpoints:
- `GET /health` - Health check endpoint
- `POST /orion` - Accepts JSON `{ "instance": "127.0.0.1:38937", "context": "...", "clineCommand": ["cline", ...] }` and returns `{ "exitCode": 0, "stdout": "...", "stderr": "...", "timestamp": "..." }`

The proxy ensures safe command execution and provides additional services:
1. **Instance Management**: Checks if the specified Cline instance is running, starts it if not.
2. **Context Setting**: Automatically sets the provided context on the instance before executing the command.
3. **Command Execution**: Executes the Cline command with proper quoting and timeout handling.

This provides a clean interface for the Windows host to communicate with Cline on the Linux VM while offloading instance and context management.

### Security and Configuration:
- The wrapper assumes Cline is already installed and configured on the VM
- The HTTP proxy provides an additional security layer by validating commands before execution
- No API keys or model configurations are needed in the wrapper - Cline handles these
- All data is stored locally in JSON files, keeping your information private

This wrapper system creates a reliable, automated pipeline between your chat interface and Orion's AI capabilities, enabling structured TDD workflows without manual intervention.
