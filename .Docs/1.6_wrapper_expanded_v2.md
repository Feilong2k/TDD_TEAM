# 1.6 Orion Wrapper: Expanded Explanation v2

## 1. Functions of the Wrapper Script for Orion

The wrapper script is the bridge between your chat interface and the Cline AI coding agent. It handles communication with Orion (the AI agent) via a secure HTTP proxy and ensures he responds in a structured way that your system can understand and use.

### What the Wrapper Does:
1. **Receives Messages**: Takes a user's message from the chat interface along with project/task context and mode (Plan/Act).
2. **Prepares the Prompt**: Combines Orion's instructions (system prompt) with the conversation history and the new message.
3. **Calls Cline via Proxy**: Uses an HTTP proxy (running on the VM) to execute Cline commands, creating new non-interactive tasks.

   **Response:** Start with a **3-minute timeout** as you suggested. For handling "stuck" tasks, instead of a complex restart mechanism initially, we can implement a **Stream Monitoring** feature in the future. The proxy could listen to the output stream; if no new output appears for >2 minutes, it terminates the request. For now, a simple timeout at the HTTP proxy level is the easiest first step.
4. **Validates Responses**: Checks that Orion's response is valid JSON and matches the expected structure.
   NOTE: are we using Regex to extract JSON portion of the response? so type of warning should be excluded

   **Response:** **Yes**, we should definitely use Regex. LLMs often output "Here is your JSON:" or warnings before the actual JSON. A regex like `/\{[\s\S]*\}/` (finding the first `{` and last `}`) is standard practice to extract just the JSON payload and ignore surrounding noise.
5. **Handles Retries**: If Orion doesn't respond with valid JSON, it asks again (up to two times) with reminders about the required format.
6. **Saves Conversations**: Keeps track of all messages in JSON files, organized by project and task.
7. **Updates Task Status**: When Orion indicates a task status change, the wrapper updates the task tracking file automatically.

9. **Manages Errors**: Logs any problems to a file so you can troubleshoot issues later.

## 3. JSON Files and Their Detailed Structures

### tasks.json
Located at: `data/tasks.json`

**Purpose**: Central registry of all tasks across projects.

**Full Structure**:
```json
{
  "tasks": {
    "P-001-T-001": {
      "id": "P-001-T-001",
      "project_id": "P-001",
      "title": "Optional title from decomposition",
      "description": "Optional description",
      "status": "pending|in_progress|completed|blocked",
      "created_at": "2025-12-12T23:54:24.614Z",
      "updated_at": "2025-12-12T23:54:24.614Z",
      "last_message": "Optional last message about this task",
      "assignee": "Tara|Devon|Orion",
      "subtasks": [
        {
          "id": "P-001-T-001-1",
          "title": "Write failing test",
          "description": "...",
          "assignee": "Tara",
          "status": "pending"
        }
      ]
    }
  },
  "last_id": "P-001-T-001"
}
```

**Field Details**:
- `tasks`: Object where keys are task IDs and values are task objects.
- `id`: Unique identifier following pattern `{projectId}-T-{sequence}`.
- `project_id`: Reference to the project this task belongs to.
- `status`: Current state; must be one of: `pending`, `in_progress`, `completed`, `blocked`.
- `created_at`/`updated_at`: ISO 8601 timestamps.
- `last_message`: Most recent message from Orion about this task.
- `assignee`: Which agent is currently responsible (Tara for tests, Devon for implementation, Orion for planning).
- `subtasks`: Array of subtasks from decomposition (optional).
- `last_id`: The highest task ID generated, used for auto-increment.

### Conversation Files
Located at: `data/conversations/project_{id}.json` and `data/conversations/task_{id}.json`

**Purpose**: Store message history for projects and tasks.

**Full Structure**:
```json
{
  "conversations": [
    {
      "role": "user|assistant",
      "content": "For user: plain text. For assistant: JSON string of Orion's response.",
      "timestamp": "2025-12-12T23:54:24.614Z",
      "message_id": "optional_unique_id"
    }
  ],
  "metadata": {
    "project_id": "P-001",
    "task_id": "P-001-T-001",
    "last_updated": "2025-12-12T23:54:24.614Z",
    "message_count": 5
  }
}
```

**Field Details**:
- `conversations`: Array of message objects in chronological order.
- `role`: `user` for human messages, `assistant` for Orion's responses.
- `content`: For assistant messages, this is the stringified JSON of Orion's response.
- `timestamp`: ISO 8601 timestamp of when the message was sent/received.
- `message_id`: Optional unique identifier for each message (could be used for deduplication in polling).
- `metadata`: Additional information about the conversation file.

## 4. Response JSON Structure Details

### Common to All Response Types
```json
{
  "response_type": "clarification|decomposition|instruction|status_update|conversation",
  "content": { /* type-specific content */ },
  "metadata": {
    "task_id": "string|null",
    "project_id": "string",
    "requires_action": "boolean",
    "next_step": "string|null",
    "timestamp": "ISO 8601 string"
  }
}
```

### Type-Specific Content Structures

1. **clarification**:
```json
"content": {
  "questions": ["Question 1", "Question 2", ...]
}
```

2. **decomposition**:
```json
"content": {
  "subtasks": [
    {
      "id": "string (e.g., T-001-1)",
      "title": "string",
      "description": "string",
      "assignee": "Tara|Devon",
      "status": "pending|in_progress|completed|blocked"
    }
  ]
}
```

3. **instruction**:
```json
"content": {
  "instructions": "Detailed step-by-step instructions for the assigned agent.",
  "assignee": "Tara|Devon",
  "expected_outcome": "string"
}
```

4. **status_update**:
```json
"content": {
  "updates": [
    {
      "id": "task or subtask ID",
      "status": "pending|in_progress|completed|blocked",
      "message": "Optional explanation"
    }
  ]
}
```

5. **conversation**:
```json
"content": {
  "message": "Natural language response to the user."
}
```
